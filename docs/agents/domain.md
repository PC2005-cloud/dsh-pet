# 领域文档

工程类技能在探索代码库时应如何消费本仓库的领域文档。

## 探索前先读这些

- 仓库根的 **`GLOSSARY.md`**，或
- 仓库根的 **`GLOSSARY-MAP.md`**（若存在）：它指向每个上下文各一份 `GLOSSARY.md`，读取与当前话题相关的那些。
- **`docs/adr/`**：读取与你即将改动的区域相关的 ADR。多上下文仓库还要检查 `src/<context>/docs/adr/` 下的上下文级决策。

上述文件若不存在，**静默继续**。不要指出它们缺失，不要主动建议先创建。`/domain-modeling` 技能（经由 `/grill-with-docs` 与 `/improve-codebase-architecture` 触达）会在术语或决策真正定下来时按需创建。

## 文件结构

本仓库是**单上下文**（single-context）：

```
/
├── CLAUDE.md
├── GLOSSARY.md
├── docs/
│   ├── adr/
│   │   ├── 0001-xxx.md
│   │   └── 0002-xxx.md
│   └── agents/          ← 本目录
└── dsh-pet/             ← 实际的 npm 包与源码
```

## 使用术语表的词汇

当你的输出要命名一个领域概念（issue 标题、重构提案、假设、测试名）时，使用 `GLOSSARY.md` 里定义的词。不要漂移到术语表明确回避的同义词。

若需要的概念还不在术语表里，这是一个信号：要么你在发明项目不用的语言（重新考虑），要么确实有缺口（记下来交给 `/domain-modeling`）。

## 指出 ADR 冲突

若你的输出与已有 ADR 相矛盾，明确暴露出来，不要静默覆盖：

> _与 ADR-0007（事件溯源订单）冲突，但值得重开，因为……_
